# JP Doc Agent｜日本語ドキュメント調査エージェント

基于真实日语公开文档的调研助手：理解用户问题，主动检索、阅读和补充证据，生成附带来源与页码的日语回答。

面向日本企业的 Agent / LLM 应用开发岗位，重点展示日语 RAG、工具调用、效果评测和后端工程能力。项目采用公开数据集，自行实现数据处理、检索和 Agent 流程。

> 当前状态：已完成环境初始化和 PDF 导入，已接入 Fujitsu RAG Hard Benchmark 的 5 份 PDF、170 页，并单独下载原始问答标注。RAG 和 Agent 功能待开发。启动方式见 [本地开发指南](docs/development.md)，导入流程见 [文档导入说明](docs/document-import.md)。

## 1. 要解决什么问题

日语报告、行政资料和企业说明文档通常分散在大量 PDF 中。用户需要反复查找、阅读和核对出处，普通聊天回答又难以确认依据。

本项目让用户用日语提问，由 Agent 查找相关资料、阅读原文；信息不足时调整检索条件，最终输出可核查的答案。

示例需求（用于说明交互，不是数据集原题）：

> この資料に記載されている制度の対象者と申請条件を整理し、根拠となるページを示してください。
>
> 整理这份资料中制度的适用对象和申请条件，并注明依据所在页码。

预期回答包含：结论、分项说明、对应证据、文档名称、来源链接及 PDF 页码。资料无法回答的问题，应说明缺少什么信息。

## 2. 使用哪些真实数据

| 数据来源 | 内容 | 在项目中的用途 |
| --- | --- | --- |
| [Fujitsu RAG Hard Benchmark](https://github.com/FujitsuResearch/Fujitsu-RAG-Hard-Benchmark) | 日语 RAG 评测集，提供部分原始 PDF、100 道问答和证据页码 | 当前主数据源，用真实资料开发导入和 RAG，再用原始标注评测 |
| [JQaRA](https://github.com/hotchpotch/JQaRA) | 基于日语 Wikipedia 等来源构建的检索评测数据，每个问题对应 100 条候选文本 | 后续独立比较检索和重排效果，不作为企业文档问答的正确答案 |

首版固定使用富士通数据集的 5 份 PDF，并保留上游版本、原始文件名、获取时间、文件哈希、解析器版本及失败原因。当前文档覆盖 16 道原始问题的全部证据，问答单独保存在评测目录，不进入正文库。后续按官方清单扩充文档，逐步增加可评测的问题。

数据集中部分问题需要图表理解。首版先评测可由正文回答的子集，公开筛选规则和题目 ID；复杂表格及视觉问答留待后续支持，不把子集成绩写成完整数据集成绩。

富士通仓库的软件采用 Apache-2.0，PDF 则受独立条款约束，仅用于基准评测，不能重新分发或直接作为商业产品数据。项目只提交下载代码和来源清单，原始文件留在本地。版本、子集与使用范围见 [数据来源](sources/README.md)。

## 3. 首版功能需求

| 模块 | 需要实现的功能 | 完成标准 |
| --- | --- | --- |
| 文档导入 | 下载 PDF，按页提取正文、切分段落，记录来源和页码，避免重复导入 | 同一文件重复导入不产生重复记录；每个段落能定位原文 |
| RAG 检索 | 将日语问题和段落转换为向量，检索相关内容，支持文档范围过滤 | 返回证据文本、文档 ID、来源和页码 |
| 基础问答 | 用一次检索的结果生成日语答案，作为对照版本 | 回答带引用，证据不足时明确说明 |
| Agent 调研 | 拆解问题，调用工具检索和阅读，必要时改写问题再次检索 | 能展示多次工具调用及停止原因，最多进行 3 轮检索 |
| 引用检查 | 检查引用的文档、页码和片段确实存在，支持打开原文 | 引用可追溯；答案是否被证据支持另行评测 |
| 运行记录 | 保存任务状态、工具调用、耗时、模型用量与错误 | 能复现失败过程，并比较不同方案的效果与成本 |

日语是默认输入和输出语言。保留原文中的名称、数字、单位和日期；展示 PDF 物理页码，避免与文档印刷页码混淆。

## 4. Agent 如何工作

```text
日语问题 → 确定检索范围与子问题 → 调用检索工具 → 阅读证据
                                                    ↓
                                  判断证据是否足够回答
                                    ↙             ↘
                           改写问题再次检索      生成答案和引用
                                    ↓
                           达到上限仍不足则说明缺失信息
```

首版提供三个只读工具：

- `search_documents`：根据问题及文档范围检索相关段落。
- `read_document_page`：读取指定文档页面，补充段落周围的上下文。
- `get_document_metadata`：查询文档标题、来源及可用的日期信息。

RAG 负责找到证据，Agent 负责决定查什么、何时补查以及何时停止。文档内容只作为资料，不能改变系统规则或工具权限；任务设置超时和调用次数上限。

首版采用单 Agent，在已导入的文档内工作。联网搜索、OCR、多模态图表理解和多 Agent 协作作为后续扩展。

## 5. 开发环境与技术选型

以下为整体技术方案。当前已配置 Python、数据库和基础开发工具，实际依赖版本锁定在 `uv.lock`；其他组件随对应功能加入。

| 项目 | 计划使用 | 用途 |
| --- | --- | --- |
| 本地环境 | macOS Apple Silicon；Docker Desktop | 本地开发和数据库运行 |
| Python 环境 | Python 3.12 + uv | 依赖管理、虚拟环境和版本锁定 |
| 后端服务 | FastAPI + Pydantic | 问答接口、参数校验和结构化结果 |
| Agent 流程 | [LangGraph](https://docs.langchain.com/oss/python/langgraph/overview) | 管理检索、阅读、判断和结束状态 |
| PDF 解析 | pypdf + pdfminer.six | pypdf 校验文件与页数，pdfminer.six 处理日语正文及字体映射；不负责 OCR |
| 数据库 | PostgreSQL 17 + [pgvector](https://github.com/pgvector/pgvector) | 保存文档信息、段落向量和任务记录 |
| 数据库访问 | SQLAlchemy + Alembic | 数据访问与表结构迁移 |
| 模型服务 | 支持日语及工具调用的 LLM API；支持日语的 Embedding 模型 | 推理和向量化，模型名称通过配置指定 |
| 检查与测试 | pytest + Ruff | 测试核心行为、检查代码质量 |
| 演示界面 | 后续增加 Streamlit | 日语提问、答案引用及执行步骤展示 |

先采用云端模型 API，避免本地部署大模型成为前置条件。需要准备模型服务账号及 API Key，并记录调用费用；密钥放入 `.env`，不提交到 Git。

数据库使用独立的 Docker Compose 配置和持久化数据卷。pgvector 是需要安装并启用的 PostgreSQL 扩展，普通 PostgreSQL 镜像不自动具备向量检索能力。模型或向量维度变更时，需要重建对应向量数据。

## 6. 如何证明项目有效

先建立“单次检索 + 回答”的基线，再在相同文档、问题和模型下比较 Agent。之后分别加入日语分词的关键词检索、混合检索及重排，每次记录改动和结果。

| 评测方面 | 观察什么 |
| --- | --- |
| 检索效果 | 富士通子集中正确证据页是否进入前 K 个结果；JQaRA 单独报告 nDCG@10 |
| 回答质量 | 根据现成参考答案检查关键事实，数值题核对数字和单位，抽样人工复核 |
| 引用质量 | 引用是否可打开，以及原文是否真正支持对应结论 |
| 无答案处理 | 对无法回答的问题能否说明证据不足，避免编造 |
| Agent 收益 | 补充检索是否解决基线失败的问题，是否增加无效调用 |
| 运行开销 | 每题耗时、调用次数、Token 用量及估算费用 |

按文档划分开发集和测试集；允许索引测试文档正文，但参考答案不能进入检索库或生成提示词。固定测试集后不据此反复调参，记录模型、提示词和数据版本。

利用富士通数据集的多步推理、跨文档和证据标注，分别评测基础问答与 Agent；仅评测当前语料覆盖全部证据的题目。所有成绩实测后填写，接受 Agent 在部分任务上不优于基线的结果。
